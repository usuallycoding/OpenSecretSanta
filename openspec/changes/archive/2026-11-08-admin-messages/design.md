# Design

## Context

`SendAnnouncement` checks the owner, the state, the title, the message and the channels, sends the emails, plans the pushes and returns the counts; nothing is stored, and `AnnouncementRoutes.kt` says so. Letters are the nearest model for keeping something: a table keyed by group and a number (`V011__letters.sql`), a SQLite repository whose write takes the lock with `UPDATE groups SET state = state WHERE id = ? AND state = ...`, checks the cap and inserts the next number, `ParticipantGroupLoader` for participants and `OwnedGroupLoader` for the owner. Migrations are listed in `server/resources/db/migration/index.txt`; the last is V013.

On the client, `GroupInfoCard` draws the description card and, only if one of the three is set, the information card; both the group page and the admin screen use it. `CardIconButton` already gives an outlined icon button with a tooltip and an optional badge, `MailIcon` is the letter icon and `Icons.Filled.Notifications` the bell, `LazyPullPage` and `loadItems` give a lazy list, and the admin screen already lays out a pane beside the page (`Row` with `PANE_WIDTH`, `GroupSheet.opensInPane()`). The participant group page has no pane and is not a spread page. A notification tap is mapped by `NotificationTarget.routesOf(category, groupId)`. See proposal.md for why and what.

One fact shapes the push side: the category "announcements" is used by three kinds of notification, the owner's announcement, "added to a group" and "names drawn" (`groupVisible`, `groupDrawn`), so the category alone cannot tell the one that should open Group Notifications.

## Goals / Non-Goals

**Goals:**
- Keep what the owner announces and show it, newest first, to participants and the owner.
- Follow the patterns of letters and the admin pane, so that the change adds little that is new.

**Non-Goals:**
- A new-message indicator, badges and read marks: the change `admin-messages-unread`.
- Editing or deleting a sent announcement, paging the list, or showing which channels were used or who sent it.
- Messages sent before this change: they were never kept.

## Decisions

**A table of its own, numbered per group.** `V014__announcements.sql` adds `announcements (group_id, number, title, body, sent_at)` with the primary key (group_id, number) and a foreign key on `groups` with `ON DELETE CASCADE`, so deleting a group deletes them. `sent_at` is milliseconds, as for letters. The port `AnnouncementRepository` has `add(groupId, title, body, atMillis, max)`, which in one transaction takes the group's write lock (the group must be Pending or Active), refuses with `InvalidState` at `max`, and inserts the next number, and `list(groupId)` ordered by number. The limit is its own constant, `AnnouncementLimits.MAX_PER_GROUP = 200`, like the other limits.

**`SendAnnouncement` keeps before it sends.** After the existing checks and before any email or push plan, it calls `add`; the 201st therefore fails with 409 before anything is sent, and an announcement is kept even when every email fails. If keeping it throws, nothing is sent, which matches "everything is checked before anything is sent". It gains a `Clock`. Alternative rejected: keeping after sending. A failed write would then leave people notified of a message nobody can read.

**Two read routes, one use case.** `GET /groups/{id}/announcements` for participants (`ParticipantGroupLoader`, so a Draft, a stranger or a missing group is 404) and `GET /admin/groups/{id}/announcements` for the owner, who may not be a participant (`OwnedGroupLoader`, with a Draft answered 409), both returning `AnnouncementDto(number, title, body, sentAt)` in the order sent, like letters; the client reverses them. The admin path is the one `POST` already uses. Alternative rejected: one route for both. The participant loader answers 404 for an owner who is not in the group, and the admin routes carry the administrator check.

**A mark on the push message, not a new category.** `PushMessage` gets `target: String? = null`; `planAnnouncement` sets it to `messages`, `groupVisible` and `groupDrawn` leave it null. `FcmPushSender` adds it to the data as `NotificationData.TARGET` when set, and the Android service passes it on with the group and the category. `NotificationTarget.routesOf(category, groupId, target)` adds `AnnouncementsRoute` for `announcements` with the target `messages`, and keeps opening the group for the rest. Alternatives rejected: a sixth category, which would add a settings switch and change `allows`, and telling the kinds apart by their text. Android and the web app receive pushes (the web app through its service worker and `push.js`), so both read the key: the service worker's own copy of the address mapping gets the same case.

**The information card is always drawn and holds the icon.** `GroupInfoCard` keeps the description card optional and always draws the information card with three lines, a missing value shown as `TBD` (`Strings.TBD`). The date and time line stays what `formatWhen` returns, so a date alone shows the date and `TBD` replaces the line only when it returns null. The card becomes a `Row`: the three lines in a column that takes the width, and at the end the icon, vertically centered. The icon is a `CardIconButton(Icons.Filled.Notifications, "Group Notifications", ...)`, a bell, which already gives the tooltip and the spoken name, drawn only when the caller passes an `onOpenMessages` (a Draft group's page and screen pass none). The screen-reader text of each line is unchanged. The bell is also the icon of the owner's "Send announcement" button on the admin screen; it is kept because the request was for a bell, and the tooltip names it. A distinct icon for one of the two is a one-line change if they get mixed up. (The letter icon was the first choice and was changed to the bell, so that the page is named for notifications.)

**The page is a lazy list with its own view model.** `AnnouncementsViewModel(groupId, forOwner, api)` loads with a `Loader`, reads through `api.groupAnnouncements` or `api.adminGroupAnnouncements`, maps to `AnnouncementItem(number, title, text, sent)` with `formatInstant` and sorts by number, newest first. `AnnouncementsPage` is a `LazyPullPage` with `loadItems`, `items(key = number)` of an `AnnouncementCard` (title, message and a `TimesLine`, built like `LetterCard` without the new pill), and one item for the empty text. It is used as a page, in a pane and for both views.

**A page on small screens, a pane on wide windows, both at the notifications' address.** Two routes, `AnnouncementsRoute(groupId)` and `AdminAnnouncementsRoute(id)`, with the addresses `#/groups/{id}/notifications` and `#/admin/groups/{id}/notifications` in `WebAddresses`. The icon always navigates to its route (with `launchSingleTop`, so a second tap opens nothing more). On a small screen the route is a page. On a wide window the same route renders the group's page with the pane beside it: the participant group page lays out a `Row` like the admin screen (the page centered at the readable width, the pane at `PANE_WIDTH` with a header holding "Group Notifications" and a close button), which makes `GroupRoute` and both announcements routes spread routes in the shell, as `AdminGroupRoute` already is. The pane is therefore the route's, not state of the screen, so the browser's address follows it: `#/groups/2` becomes `#/groups/2/notifications` when it opens and returns when it closes, and the browser's back button closes it. Closing the pane navigates to the group's own route, popping the announcements route (`launchSingleTop` reuses the group entry that is below it), which also covers a pane opened by an address or a notification. `GroupEntry` and `AdminGroupEntry` in `ShellScreen.kt` build the page for both routes. On the admin screen a pane of the screen's own state (rules, a wishlist, a pair) shows first when one is open and gives way to the announcements when closed, and the icon closes it. The top bar shows its back arrow for a screen below the groups, so both routes are added to the screens that count as below a group (`belowGroups` and `belowAdminGroups` in `ShellScreen.kt`); the title is "Group Notifications" on a small screen and the group's own title on a wide window, where the pane carries the heading. In the sidebar the route keeps Overview selected. Alternative rejected: the pane as state of the group's view model, as the rules pane is. It keeps the group page's scroll place, but the address cannot follow state, because the browser binding writes the address from the destination only, and the icon sits near the top of the page, so little is lost. The group page is composed afresh for the route, which resets its scroll to the top.

**No change to the owner's send sheet.** It already shows the server's refusal text, so the 409 for 200 announcements appears there as it is.

## Risks / Trade-offs

- [The group page is composed again for the announcements' route on a wide window, so it starts at the top] → The icon is in the card near the top of the page, so a person who opens the pane has seldom scrolled far. Check that closing the pane (the arrow, the close button and the browser's back) lands on the group page, and that an address or a notification opened on its own closes onto the group page, not the group list.
- [The bell stands for two things on the admin screen: the card's Group Notifications and the "Send announcement" button below it] → The card's icon has the tooltip and spoken name "Group Notifications" and sits in the information card, while the button is one of the actions below it and is named "Send announcement". Changing one of the icons is a one-line change.
- [The card now takes room on every group page, with three `TBD` lines for a group with no details] → Wanted: the icon needs a home and the layout stays the same for every group.
- [200 announcements of 2000 characters are about 400KB in one response] → Bounded and rare, and the page draws only what is on screen; paging is a non-goal until it hurts.
- [Existing tests that assume the card is left out for a group with no details, or that build a `PushMessage` or a `SendAnnouncement`] → Updated in the tasks that change those, not collected at the end.
- [Messages sent before this change are not there] → Said in the proposal; nothing can bring them back.

## Migration Plan

The migration only adds a table, so the server can be deployed first. Clients without the page ignore the new routes, and a new client talking to an old server shows its load failure on the page. Rolling back the code leaves an unused table, which can stay.
